# vttestserver-operator: guide for AI agents and new contributors

## What this repository is

A Kubernetes operator (kubebuilder v4 layout, controller-runtime) for Vitess `vttestserver`. Read
[README.md](README.md) first.

## How it works

| Object | What the operator creates |
|---|---|
| `VTTestServer` | A StatefulSet with one pod, a Service for MySQL (port 15003), a Service for vtctld gRPC (port 15001), and ConfigMaps for settings. |
| `VTTestServerSnapshot` | A Job that stops the server, uploads its data directory (a `tar.zst` file) to S3, and starts the server again. |

A server goes through the phases `Pending`, `Restoring`, `Starting`, `Configuring` and `Ready`. `Ready` means
that vtgate accepts connections and the VSchema and SQL are applied. `datactl` is a small helper program, in
its own image. The operator uses it in init containers and Jobs to restore, snapshot and delete snapshot data.

## Metrics

Served on the metrics port of the chart, next to the standard controller-runtime metrics:

| Metric | Meaning |
|---|---|
| `vttestserver_operator_servers{phase}` | Servers by phase. Alert on `Failed`. |
| `vttestserver_operator_snapshots{phase}` | Snapshots by phase. |
| `vttestserver_operator_snapshot_oldest_phase_age_seconds{phase}` | Age of the longest running snapshot in Pending, Quiescing, Uploading or Deleting. Alert on a high value. |
| `vttestserver_operator_snapshot_duration_seconds` | Summary of the time from creation to a finished upload. Only the leader records it. |
| `vttestserver_operator_snapshot_failures_total` | Snapshots that ended `Failed`. Only the leader records it. |

## Releasing

Pushing a tag matching `v*` runs `.github/workflows/release.yaml`: it builds and pushes the `manager` and
`datactl` images (multi-arch, `linux/amd64`/`linux/arm64`) and the Helm chart to `ghcr.io`, and publishes
standalone `datactl` binaries (`linux`/`darwin`, `amd64`/`arm64`) to a GitHub release, with everything's
version derived from the git tag. `dist/chart/values.yaml` defaults `manager.image.repository` and
`datactl.image.repository` to the published `ghcr.io` paths, so the published chart installs with no `--set`
overrides. The `binaries` job (GoReleaser, config in `.goreleaser.yaml`) only runs on an actual tag push, not
on a manual `workflow_dispatch`, since it needs a tag ref to derive the version from.

Each image gets an SPDX SBOM and SLSA provenance attestation (`sbom: true`/`provenance: true` on
`docker/build-push-action`), and is signed keyless with `cosign`, using the workflow's own GitHub OIDC
identity through Sigstore (Fulcio/Rekor) — no signing key to manage. Verify a release image with:

```sh
cosign verify ghcr.io/likesavabutworse/vttestserver-operator:<tag> \
  --certificate-identity-regexp '^https://github\.com/likesavabutworse/vttestserver-operator/\.github/workflows/release\.yaml@.*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

(swap `vttestserver-operator` for `vttestserver-operator-datactl` to verify the other image.) To build your
own images for a private registry instead:

```sh
make docker-buildx IMG=<registry>/vttestserver-operator:<tag> \
  DATACTL_IMG=<registry>/vttestserver-operator-datactl:<tag>
```

## Layout

| Path | Content |
|---|---|
| `api/v1alpha1/` | The CRD types and their validation rules (CEL). `zz_generated.deepcopy.go` is generated. |
| `cmd/main.go` | The operator. |
| `cmd/datactl/` | `datactl`: snapshot, restore, delete and `apply-my-cnf`. It must not import `api/v1alpha1` or Kubernetes packages. |
| `internal/controller/` | The two controllers, the builders for the generated objects, the metrics, the tests, and `testdata/` (golden files). |
| `internal/snapshot/` | Archive, store (S3 and in-memory), take and restore. `manifest/` has the standard library only. |
| `internal/vitess/` | The client for vtctld (VSchema) and vtgate (SQL). |
| `config/crd/bases/`, `config/rbac/role.yaml` | Generated by `make manifests`. Do not edit. |
| `dist/chart/` | The Helm chart. It is maintained by hand. |
| `dev/`, `Tiltfile` | The development setup and the test workflow. |
| `examples/`, `docs/` | User documents. |

## Rules

- Do not edit generated files: `config/crd/bases/*`, `config/rbac/role.yaml`, `zz_generated.*`. After a change in
  `api/` or in a `+kubebuilder:rbac` marker, run `make manifests generate`.
- The chart has a copy of the CRDs and of the ClusterRole rules. After `make manifests`, copy them into
  `dist/chart/templates` and run `make helm-check`. The check fails when they differ.
- Do not remove the `// +kubebuilder:scaffold:` comments.
- The operator keeps its state in the `status` of the objects, not in memory.
- A change to the generated StatefulSet or Jobs restarts every server on the next operator start. The golden-file
  test fails first: `go test ./internal/controller -run TestGeneratedObjectsAreStable`. Update the files with
  `-update-golden` and write a release note.
- Put no internal or production information in this repository: no real database or keyspace names, VSchemas,
  bucket names or ticket numbers. Test data is synthetic or comes from the Vitess examples (Apache-2.0).
- Write a failing test first for a bug fix.
- Write documents in short sentences and plain words.

## Test and run

```sh
make test         # unit tests and envtest
make lint
make helm-check   # helm lint, and the chart against the generated CRDs and RBAC rules
tilt up           # the full workflow on a local cluster; see README.md
```

S3 tests use an in-process fake server. To run them against real S3 compatible storage, set `VTTEST_S3_ENDPOINT`
(see `internal/snapshot/s3_integration_test.go`).

## Facts about `vttestserver`

- It has no authentication and no native backup (`Backup` is not implemented in vtcombo), so a snapshot is a tar
  of the data directory after a clean stop.
- The image takes no extra arguments, so the operator sets the command (`/vt/bin/vttestserver`) and owns the
  flag list. Test each supported image tag, because a flag that the image does not know crashes the pod.
- vtctld `ApplySchema` is not implemented in vtcombo. The operator applies SQL through vtgate over the MySQL
  protocol. `ApplyVSchema` works and replaces the VSchema of a keyspace.
- `my.cnf` is written once, when Vitess first initialises a data directory. For that reason an init container
  (`apply-my-cnf`) rewrites it from `spec.mysqlConfig` on every pod start.
